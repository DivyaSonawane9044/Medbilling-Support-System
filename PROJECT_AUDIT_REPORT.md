# MedBilling Support System — Project Audit Report

**Audit date:** 2026-10-31
**Scope:** The full repository, covering Git state, the frontend (React/Vite), the backend (Spring Boot), the database, security, and build/test.
**Method:** I recovered the source from Git and built both original projects without any changes. I ran the original backend and called every GET endpoint plus the main write endpoints with `curl`. I did a static review of every controller, service, entity and frontend page. Two independent reviewers covered the frontend pages and their findings were cross-checked against the backend code. Where possible, each finding below was reproduced live. Findings that came only from code review are marked *(code)*.

This report describes the project **as found**, before any fixes. For what was changed, see `BUG_FIX_REPORT.md`. For test results, see `TESTING_REPORT.md`.

## 4. Architecture as found

- **Frontend:** React 18.3, Vite 5, React Router 6, Axios, Clerk (`@clerk/clerk-react` 5), Recharts 3, lucide-react, jsPDF and html2canvas. The API base URL is hardcoded to `http://localhost:8081` in `services/api.js`. The Clerk publishable key is hardcoded in `main.jsx`.
- **Backend:** Spring Boot **4.0.0**, Java 17 target, Spring Data JPA / Hibernate 7.1, H2, MySQL connector, PostgreSQL driver (unused), Razorpay SDK 1.4.6, and OpenPDF 2.0.3. It has 15 controllers, 10 services, 8 repositories and 9 entities.
- **Database:**
  - The active default is an **H2 in-memory database** (`jdbc:h2:mem:testdb`, `ddl-auto=create-drop`), so **all data is lost on every restart**.
  - An optional `mysql` profile exists (`pharmacy_db`), with the `root/root` password hardcoded.
  - The H2 console is enabled but answered 404.
  - `DataInitializer` seeds about 300 random demo medicines, 100 customers, 100 suppliers and 215 invoices on every start.

## 5. Findings, by severity

### CRITICAL

| # | Area | Finding | Evidence |
|---|---|---|---|
| C1 | Security | **The backend has no authentication or authorization.** There is no Spring Security, and every `/api/**` endpoint (customers, payments, reports, deletes) is open to anyone who can reach port 8081. The server binds `0.0.0.0`. Clerk only hides frontend routes. | Live: every endpoint answered without a token |
| C2 | Security | The frontend sends `Authorization: Bearer [object Promise]`: `window.Clerk.session.getToken()` is async and is not awaited. | `services/api.js` *(code)* |
| C3 | Billing | **Negative quantities are accepted.** A bill with `quantitySoldTablets: -500` created an invoice of **₹-1,440.20**, *increased* stock by 500 tablets, and saved a negative "SUCCESS" payment. | Live: stock 1071 → 1571 |
| C4 | Billing | Empty bills (`lineItems: []`) create ₹0.00 invoices and payment rows. | Live: invoice 216 |
| C5 | Payments | **Fake Razorpay success.** The backend accepts the hardcoded signature `mock_signature_dev` for any `order_mock_*` order and records a SUCCESS / RAZORPAY payment. The frontend (`utils/razorpay.js`) produces that signature itself when keys aren't configured. | Live: HTTP 200 "Payment successful and verified" |
| C6 | Payments | **Duplicate payments.** `/payments/record` and `/verify-payment` always record the *full grand total*, with no check of what has already been paid. One ₹31.69 invoice ended up with 4 SUCCESS payments (₹126.76). | Live: invoice 218 |
| C7 | Billing UI | **The prices shown on the bill are made up.** `Billing.jsx` uses `10 × (1 + profitMargin)` per tablet (or ₹15), with 12% or 5% GST. The backend uses batch selling price ÷ strip size + 12% GST. What the cashier sees and prints does not match what is saved. | *(code)* `Billing.jsx` `calcLine` |
| C8 | Billing / legal | **Customers are charged above MRP.** GST is added *on top of* the batch selling price. A strip with MRP ₹28.83 was billed at **₹31.69**. In India, MRP includes all taxes. | Live: invoice 218, batch 87 |
| C9 | Inventory | **There are two separate sources of stock.** `Product.quantity` (typed by hand, shown on most screens) is never updated by sales or purchases. Billing uses `InventoryBatch` stock only. "Aspirin" shows 1,500 in stock, but billing says "Insufficient stock" because it has no batches. | Live |
| C10 | Billing UI | Uploading a prescription sends a base64 image into `Customer.prescriptionImageUrl` (VARCHAR 255), which makes the whole sale fail and roll back. | *(code)* |

### HIGH

| # | Area | Finding |
|---|---|---|
| H1 | Customers | `PUT /customers/{id}` replaces the whole entity. The client can set `remainingBalance` (live: it reset the balance to 0) and wipes any fields not sent (contact, address and doctor became null). |
| H2 | Customers | `POST /customers/{id}/pay` accepts negative or oversized amounts (live: ₹-10,000 *raised* the balance to ₹10,308.25) and keeps no payment record. |
| H3 | Suppliers | `PUT /suppliers/{id}` with an unknown ID returns 500. The client can overwrite `ledgerBalance`. Supplier payments accept any amount and keep no history. |
| H4 | Purchases | `POST /purchases/receive` without `totalAmount` returns 500 (NullPointerException). Receiving can't be linked to a pending PO from the UI, so POs stay PENDING forever. The same PO can be received twice. There is no validation of quantity, price or expiry. |
| H5 | Errors | No `@ControllerAdvice`. "Not found", "Insufficient stock", validation and foreign-key errors all come back as **HTTP 500** with no message (live: `/sales/invoices/1` before seeding, product delete, supplier PUT). |
| H6 | Products | Deleting a product that has batches or sales returns a 500 foreign-key error. |
| H7 | Routing | `/sign-in` and `/sign-up` only match the exact path. Clerk's sub-steps (`/sign-up/verify-email-address`, `/sign-in/factor-one`, SSO callback) fall to the catch-all route, so email verification and MFA can't finish. *(code)* |
| H8 | Routing | `/medicines` and `/add-medicine` both render ProductMaster, and `/expiry-alerts` and `/stock-alerts` both render ExpiryTracking. `Medicines.jsx`, `AddMedicine.jsx`, `ExpiryAlerts.jsx` and `StockAlerts.jsx` are dead code. |
| H9 | Security | The debug pages `/auth-test`, `/debug-auth` and `/login-test` are public routes in production. |
| H10 | Billing UI | Fake customer details ("Jane Doe", "Dr. A. Sharma", "+91 98765 43210") are prefilled as real form values, so they create real customer records. `selectedCustomerId` is never cleared, so later bills attach to the previous customer. Every line item gets the last selected dosage, not its own. |
| H11 | Dashboard | "Recent Sales" is hardcoded fake data, and the trend percentages are hardcoded. "Monthly Profit" actually shows today's profit. When there is no data, the category chart falls back to made-up numbers. |
| H12 | Analytics | Every figure is read from `localStorage.rp_bills`, which nothing writes, so the page always shows ₹0. "Profit vs Expense (Mock)" is a fixed 25/75 split. |
| H13 | Accounting | Profit is hardcoded as `taxable × 25%`. The real `/api/accounting/summary` endpoint is never called. |
| H14 | Customers UI | Prescriptions are saved only in localStorage, under the key `"undefined"`, so all customers share them. "Spend" is always ₹0. The search box unmounts on every keystroke and loses focus. |
| H15 | Settings | Saving writes to localStorage only, and nothing reads it back. The users table is fake and four tabs are empty. |
| H16 | Product Master | MRP, cost price and GST % on the form are never saved (the `Product` entity has no such fields). Edits wipe `unitType`, `volumeMl` and `weightGm`. |
| H17 | Layout | The sidebar is a fixed 260px with no mobile collapse; on a phone it covers about 70% of the screen. |
| H18 | Config | The MySQL password `root` is hardcoded. CORS allows *any* origin with credentials. |

### MEDIUM / LOW (selected)

- Billing uses a single batch only. If no single batch can cover the quantity, the sale fails even when total stock is enough.
- The invoice number is `INV-<millis>`, which could collide.
- Print: there is no real `window.print()`. Ctrl+P is intercepted. The PDF says "PROVISIONAL" with no invoice number, and long bills get squashed onto one page.
- `InventoryBatchDTO` has no supplier or cost fields, so the Expiry page shows supplier "N/A" and stock value ₹0.
- The supplier history "quantity" is current remaining stock, not the quantity received.
- `/reports/customer/{id}` reports every customer's sales, not just that customer's.
- Report downloads ignore the server filename and content type.
- `Inventory.jsx` and `Dashboard.jsx` use `Promise.all`, so one failed endpoint blanks the whole page.
- The navbar search box has no handler, and the bell badge is hardcoded to "3".
- The seed data has `tabletStock ≥ stripSize` (for example 100 loose tablets on an 11-tablet strip), which is not a valid stock state.
- SMS/WhatsApp notifications only write to the log.
- `spring.jpa.open-in-view` is on by default; controllers rely on lazy loading.
- `org.json` appears twice on the classpath (warning).
- The frontend `.env.example` says port 8080, but the backend runs on 8081.

## 7. Planned remediation (in priority order)

1. Restructure into `frontend/` and `backend/`, add the Maven wrapper, and stop tracking `node_modules`/`dist`.
2. Backend security: validate Clerk JWTs (Spring Security OAuth2 resource server with Clerk JWKS) and restrict CORS. Frontend: await the Clerk token.
3. Global exception handler with correct 400/404/409 responses.
4. Billing: validation, multi-batch FEFO allocation, MRP-inclusive GST, a per-product GST rate, a server-side quote endpoint, and making the frontend show server prices.
5. Payments: no mock success, order amount set by the server, outstanding-balance checks, and failure recording.
6. Customers, suppliers and purchases: safe updates, payment validation and receiving against a PO.
7. A single source of truth for stock (batches). Product quantity becomes derived.
8. Remove fake and hardcoded data from Dashboard, Analytics and Accounting.
9. Persistent development database (H2 file mode), MySQL configured through environment variables, and opt-in demo data.
10. Automated tests: JUnit/MockMvc integration tests for business flows and security, plus Vitest for the frontend.
